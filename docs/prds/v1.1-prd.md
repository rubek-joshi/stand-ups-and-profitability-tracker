# Product Requirements Document: Profitability Tracker

**Status:** Draft v1.0
**Currency:** NPR (Nepalese Rupee)
**Default VAT Rate:** 13% (configurable)

---

## 1. Overview

The Profitability Tracker is an internal organizational tool that answers seven core questions:

1. What profit margin are we getting from each client and project — based on money actually collected, not just what was contracted?
2. Which projects are bleeding money?
3. How well are employees being utilized across projects?
4. Are projects tracking on-budget, and what's the forecasted profit/loss at completion?
5. When a project's payment stalls, is cancelled, or the client goes unresponsive, what's the true financial outcome?
6. When do client AMCs (Annual Maintenance Contracts) need to be sent?
7. How much VAT has accumulated and is still unpaid?

The system centers on **stand-ups** as the primary data-collection mechanism for employees: during a stand-up, employee time is allocated across projects, which drives cost attribution, which drives profit/loss calculations per project, client, and category. **Core members** (see §6.4) contribute a separate, always-on cost stream to every project they're assigned to, independent of stand-ups. Every project's revenue side is tracked as **contracted** (the agreed budget/extensions) vs. **realized** (what's actually been paid) — see §6.7 — since the two can diverge when clients pay late, partially, or not at all.

---

## 2. Goals

- Give leadership real-time visibility into project and client profitability, based on **money actually received**, not just what was contracted.
- Surface underperforming ("bleeding") projects before they become a problem.
- Quantify employee utilization based on actual logged contribution, not guesswork.
- Forecast whether a project will land on-budget given its fixed budget, timeline, and current cost run-rate.
- Cleanly close out projects that are cancelled mid-way or where a client stops paying, without overstating revenue that will never arrive.
- Automate AMC reminders so free maintenance windows don't quietly expire.
- Track VAT liability continuously (on money actually collected) and clear it in a controlled, auditable way.
- Maintain a tamper-evident audit trail of all system actions, visible only to super admins.

## 3. Non-Goals (v1)

- Full invoicing / payment collection workflows (sending invoices, payment gateways, dunning/reminders to clients for payment). The system lets admins **manually log payments received** for profitability tracking purposes (§6.7), but does not generate or send invoices itself.
- Payroll processing (salary is tracked for cost calculation only, not disbursed via this tool).
- Time tracking at the sub-task/hour level (allocation is done via stand-up percentage split, not timesheets).

---

## 4. User Roles

This system is for **internal operational use by Admins and Managers only** — employees and core members are not users of the system (they do not log in or have self-service access); they only exist as records managed by admins/managers.

| Role | Permissions |
|---|---|
| **Super Admin** | Full access + audit logs + system settings (VAT rate, health indicator thresholds, AMC free period, paid leave allowance) |
| **Admin** | Manage clients, projects, employees, core members, stand-ups, extensions, payments, cancellations, write-offs, AMC, clear VAT payments, configure health indicator thresholds |
| **Manager/PM** | Run stand-ups, view dashboard/profitability for assigned projects, adjust time-split, log payments received |

Exact role-permission mapping should be confirmed with stakeholders before build; assumption above is used for scoping.

## 5. Core Data Model

### 5.1 Entities & Relationships

- **Client** → has many **Projects**
- **Project** → belongs to one **Client**, one **Category**, has many **Employees** (via explicit **ProjectAssignment**), has many **Core Members** (via explicit **CoreMemberAssignment**), has many **PaymentRecords**, has one **AMC record** (once closed)
- **Employee** → has many **Salary History** entries, has many **ProjectAssignments**, has many **LeaveRecords**
- **Core Member** → has many **Salary History** entries, has many **CoreMemberAssignments**. Does **not** participate in stand-ups and has no leave/allocation-percentage concept.
- **ProjectAssignment** → links one **Employee** to one **Project** (defines which projects an employee is eligible to be allocated to during a stand-up)
- **CoreMemberAssignment** → links one **Core Member** to one **Project** (defines which projects incur a share of that core member's monthly salary as cost)
- **PaymentRecord** → belongs to one **Project**; represents a single payment actually received from the client
- **WriteOffRecord** → belongs to one **Project**; represents a portion of the outstanding balance formally deemed uncollectible, which can later be reversed
- **Category** → has many **Projects** (seeded: `Design`, `Development`; extensible)
- **Standup** → has many **StandupEntries** (one per active **employee** only — core members are never included), each entry has many **ProjectAllocations**
- **ProjectExtension** → belongs to one **Project**
- **LeaveRecord** → belongs to one **Employee**, derived from stand-up absences, tracked per calendar month
- **AuditLog** → references an **Actor** (user), an **Action**, and a **Target Entity**

### 5.2 Key Entity Fields

**Client**
- `id`, `name`, `contact_info`, `created_at`, `status` (active/inactive)

**Project**
- `id`, `client_id`, `category_id`, `name`, `budget` (fixed contracted amount, excl. VAT), `start_date`, `end_date` (together define the project's fixed **timeline**), `status` (`active`, `extended`, `closed`, `under_amc`, `cancelled`), `created_at`
- `vat_rate_applied` (snapshot at creation, defaults to org setting)
- `auto_extended` (bool — true if the system auto-flipped status to `extended` because it wasn't closed by `end_date`)
- `cancelled_at`, `cancelled_reason` (nullable — populated when status becomes `cancelled`; covers both "client cancelled mid-way" and "client went unresponsive/AWOL" scenarios; cleared if the project is later reopened, with the prior cancellation preserved in `AuditLog` for history)
- `reopened_at`, `reopened_by`, `reopened_reason` (nullable — populated when a `cancelled` project is reopened back to `active`; reopening also updates `end_date` to the new value the admin provides at that time)

**ProjectAssignment**
- `id`, `project_id`, `employee_id`, `assigned_at`, `unassigned_at` (nullable) — defines the pool of projects an employee can be allocated to in a stand-up

**CoreMemberAssignment**
- `id`, `project_id`, `core_member_id`, `assigned_at`, `unassigned_at` (nullable) — while active, this project incurs a **day-prorated share** of the core member's effective monthly salary as cost, calculated per day as `monthly_salary ÷ days in month ÷ number of currently active concurrent assignments for that core member on that day` (see §6.4 and §6.8 for the full cost model)

**PaymentRecord**
- `id`, `project_id`, `amount`, `date`, `method` (optional, e.g. "Bank Transfer", "Cash"), `note` (optional), `recorded_by`, `created_at`
- `reversal_of_writeoff_id` (nullable — set when this payment was created as part of reversing a write-off, per §6.7.5, so the two stay linked)

**WriteOffRecord**
- `id`, `project_id`, `amount`, `reason` (required), `created_by`, `created_at`, `status` (`active`, `reversed`), `reversed_at`, `reversed_by`, `reversal_reason`, `reversal_payment_id` (nullable — links to the `PaymentRecord` created when this write-off is reversed)

**ProjectExtension**
- `id`, `project_id`, `reason` (text, required), `amount` (defaults to `0` if not provided — always affects financial totals, even at 0), `is_profit` (derived), `is_auto` (bool — true for system-triggered extensions past `end_date`), `created_by`, `created_at`

**Employee**
- `id`, `name`, `email`, `current_salary`, `status` (`active`, `left`), `date_joined`, `date_left` (nullable)

**EmployeeSalaryHistory**
- `id`, `employee_id`, `salary_amount`, `effective_from`, `effective_to`, `changed_by`, `reason`

**Core Member**
- `id`, `name`, `email`, `current_salary`, `status` (`active`, `left`), `date_joined`, `date_left` (nullable)
- Structurally similar to Employee, but modeled as a **distinct entity** since core members never appear in stand-ups and their cost logic differs entirely (day-prorated salary split across concurrent projects vs. stand-up-driven allocation).

**CoreMemberSalaryHistory**
- `id`, `core_member_id`, `salary_amount`, `effective_from`, `effective_to`, `changed_by`, `reason`

**LeaveRecord** (one per absence, derived from `StandupEntry.is_absent` — employees only)
- `id`, `employee_id`, `date`, `month` (for month-wise grouping), `type` (`paid`, `unpaid` — determined automatically based on whether the employee's paid-leave allowance for the month/period has been exceeded), `standup_id`

**Category**
- `id`, `name`, `is_seeded` (bool)

**Standup**
- `id`, `date`, `status` (`draft`, `in_progress`, `completed`), `created_by`, `participants` (all active **employees** by default — core members are never listed)

**StandupEntry** (one per employee per stand-up)
- `id`, `standup_id`, `employee_id`, `is_absent` (bool), `notes_markdown` (nullable if absent), `project_allocations` (see below)

**ProjectAllocation** (child of StandupEntry)
- `project_id` (must be a project the employee has an active **ProjectAssignment** for, and the project must not be `cancelled` or `closed` — see §6.5.3), `percentage` (0–100, sum across an entry's allocations = 100 unless absent)

**AMCRecord**
- `id`, `project_id`, `set_date`, `free_until_date`, `reminder_sent_at`, `status` (`free_period`, `reminder_due`, `paid_pending`, `overdue`, `cancelled`), `cancelled_at`, `cancelled_remark` (optional)

**AuditLog**
- `id`, `actor_id`, `action` (enum, e.g. `PROJECT_CREATED`, `SALARY_UPDATED`, `VAT_CLEARED`, `EMPLOYEE_MARKED_LEFT`, `CORE_MEMBER_ASSIGNED`, `PAYMENT_RECORDED`, `PROJECT_CANCELLED`, `PROJECT_REOPENED`, `BALANCE_WRITTEN_OFF`, `WRITE_OFF_REVERSED`), `target_type`, `target_id`, `metadata` (JSON diff), `timestamp`

## 6. Feature Requirements

### 6.1 Client Management
- CRUD for clients.
- View all projects under a client with an aggregated profit/loss summary (realized, per §6.7).
- Cannot delete a client with active projects (soft-deactivate instead).

### 6.2 Project Management
- CRUD for projects; each project has a **Category**, **Client**, and **fixed Budget (excl. VAT)** and a **fixed Timeline** (`start_date` → `end_date`).
- Project status lifecycle: `Active → Extended → Closed → Under AMC`, with **`Cancelled`** reachable from `Active` or `Extended` at any point, and **reopenable** back to `Active` (see §6.7.3). (Extended is a modifier/event, not necessarily exclusive of Active — see §6.6.)
- **Auto-extension:** if a project reaches its `end_date` and has not been marked `Closed` or `Cancelled` by an admin, the system automatically flips its status to `Extended` (flagged `auto_extended = true`) so it doesn't silently sit in limbo. Further manual extensions can then be logged against it as usual (see §6.6).
- Project detail view shows: **Total Contracted Revenue**, **Total Received**, **Outstanding Balance**, **Written-Off Amount**, total attributed employee cost, total core member cost, **Realized Profit/Loss** (primary) and **Contracted Profit/Loss** (secondary) with margins, extension history, payment history, AMC status, **budget-vs-timeline forecast** (see §6.9), and utilization breakdown of employees/core members who worked on it.
- **Employee-project association:** admins/managers explicitly assign employees to a project (`ProjectAssignment`). Only employees assigned to a project are eligible to be allocated to it during a stand-up (see §6.5.3).
- **Core-member-project association:** admins/managers explicitly assign core members to a project (`CoreMemberAssignment`) — see §6.4.

### 6.3 Employee Management
- CRUD for employees, including **current salary**.
- **Salary increases:** captured as a new `EmployeeSalaryHistory` entry with an `effective_from` date. Historical profit/loss calculations use the salary that was effective during that period, not the current salary — so past stand-up cost attribution is not retroactively changed by a raise.
- **Employee leaving:** mark employee `status = left` with a `date_left`. The employee:
  - No longer appears in new stand-ups.
  - Retains all historical stand-up/allocation data for reporting.
  - Is excluded from active headcount/utilization dashboards but remains queryable in historical reports.
- **Project assignment:** admins/managers assign an employee to one or more projects (`ProjectAssignment`); this pool determines which projects that employee can be allocated to in a stand-up (see §6.5.3).
- **Leave history:** each employee's profile shows a **month-wise breakdown of unpaid leave days** (see §6.5.4), alongside their paid-leave balance/usage for the current period.

### 6.4 Core Member Management
Core members are a **separate category of paid personnel**, distinct from employees:

- CRUD for core members, including **current salary** and salary history (raises tracked the same way as employees — see §6.3).
- **Never appear in stand-ups.** Core members have no notes, no absence tracking, no leave balance, and no percentage-based allocation — they are entirely outside the stand-up workflow.
- **Added to projects directly**, via `CoreMemberAssignment` — an admin/manager assigns a core member to one or more projects.
- **Cost model — monthly salary divided across active projects, prorated by day:** a core member's effective monthly salary is divided across all projects they're concurrently assigned to **on a day-by-day basis** — e.g., a core member on 3 concurrent projects for the full month has their salary split ⅓ / ⅓ / ⅓ across those 3 projects. If they're unassigned from one project partway through the month, the split recalculates for the remaining days (e.g., 3-way split for the first half of the month, then 2-way split for the second half, once one assignment ends) rather than applying one flat divisor to the whole month. If assigned to only 1 project for the full month, that project bears the full salary.
- **Core member leaving:** mark `status = left` with a `date_left`; behaves the same as an employee leaving (removed from future cost accrual, historical data retained) — see §6.3's handling for the equivalent employee case.
- Core member cost is included in project, client, and category profit/loss totals (see §6.8) and in the budget-vs-timeline forecast (see §6.9), but core members are **excluded** from the Employee Utilization metric (§6.8), since utilization is a stand-up-derived concept that doesn't apply to them.

### 6.5 Stand-ups

#### 6.5.1 Creating a Stand-up
- A stand-up auto-includes **all currently active employees** as participants. **Core members are never included.**
- Stand-up has a date and a status (`draft`, `in_progress`, `completed`).

#### 6.5.2 Live Collaborative Stand-up
- Multiple users can open the same stand-up simultaneously.
- Real-time collaborative editing: concurrent users see **each other's live cursors** and edits (e.g., via a CRDT or operational-transform based sync, such as Yjs/Liveblocks) while editing markdown notes or allocation fields.
- Presence indicators show who else is currently viewing/editing the stand-up.

#### 6.5.3 Per-Employee Entry
For each employee listed in the stand-up:
- **Absent toggle:** marking an employee absent immediately **disables/greys out their markdown notes field** and **skips their project-allocation section** for that stand-up (no project gets time credited for that day). However, absence does **not** automatically exclude the employee from that day's **cost** calculation — see the paid/unpaid leave logic below.
- **Notes field:** free-form **Markdown** editor, per employee, for stand-up notes (only enabled if not absent).
- **Project selection:** multi-select, restricted to **only the projects the employee is explicitly assigned to** (via `ProjectAssignment`, §6.2) **and that are not `Cancelled` or `Closed`** — an employee cannot be allocated to a project they aren't associated with, or to one that's no longer active.
  - On selection, the system **automatically splits time 100% evenly** across the selected projects (e.g., 2 projects → 50/50, 3 projects → 33.33/33.33/33.34).
  - The percentage split is **manually adjustable** per project (e.g., drag slider or numeric input), with validation that the total always equals 100%.

#### 6.5.4 Paid Leave, Unpaid Leave & Absence Handling
- Each employee is entitled to a configurable number of **paid leave days** — default **4 days** — set org-wide in Settings (super admin only, since it affects historical cost baselines).
- When an employee is marked absent in a stand-up:
  - If their **paid leave balance for the relevant period has not been exhausted**, the absence is recorded as a **paid leave day**: the employee is **still included in that day's cost calculation** (their prorated daily cost is still counted as an organizational cost) even though no project allocation exists for that day (since no work was logged).
  - Once an employee's absences in a period **exceed their paid leave allowance**, subsequent absences are recorded as **unpaid leave**: from that point, the employee is **excluded from cost/contribution calculation** for those specific absent days.
- **Unpaid leave history:** for each employee, the system must show a **month-wise breakdown** of unpaid leave days taken (date, count per month, running total), so patterns of excessive absence are visible.
- Paid leave balance **resets monthly**: each calendar month, every active employee's paid leave allowance refreshes to the configured amount (default 4 days); unused days do not carry over to the next month.
- This entire section applies to **employees only** — core members have no leave concept since they never appear in stand-ups.

#### 6.5.5 Stand-up Completion
- Once marked `completed`, allocations become locked and feed into profitability and utilization calculations (editing after completion should be a permissioned, audit-logged action).

### 6.6 Project Extension
- From a project, a user can add an **Extension**:
  - **Reason** (required, free text).
  - **Amount** (optional — if not provided, it **defaults to `0`**. Regardless of whether an amount is entered, every extension is a financial event that **affects the project's contracted revenue total** — a zero-amount extension simply has no monetary impact but is still logged and factored into the recalculation for consistency).
  - Extensions can be **manual** (admin/manager-initiated) or **automatic** (system-triggered when a project passes its `end_date` unclosed — see §6.2). Auto-extensions are flagged `is_auto = true`, carry `amount = 0`, and use a **fixed system-generated reason** (e.g., "Automatically extended — project was not closed by its end date"). This reason text is not editable, to keep a clear, consistent audit trail distinguishing system actions from manual ones.
  - When a project is auto-extended, the system **sends an email notification to all admins** (org-wide, not just those tied to the specific project/client) so the auto-extension doesn't go unnoticed.
- An extension's amount is added to the project's **Total Contracted Revenue** (§6.7) — it does not become "real" money until a corresponding payment is logged and received.
- The system determines and visually indicates whether the extension amount represents **profit** (client paid more than the additional cost incurred) or **loss** (extension granted for free / cost incurred exceeds amount), based on the realized figures once payment is received.

### 6.7 Payment Tracking, Cancellation & Bad Debt

This is the layer that reconciles what was **contracted** against what was **actually collected** — critical for projects where a client pays late, only partially, cancels mid-way, or disappears.

#### 6.7.1 Contracted vs. Realized Revenue
- **Total Contracted Revenue** = `Project Budget + Σ Extension Amounts`. This is the agreed-upon full value of the project — a ceiling, not a guarantee.
- **Payments** are logged individually against a project via `PaymentRecord`: an admin/manager enters an **amount** and **date** whenever the client actually pays (partial or full), with optional method/note. Multiple payments can be logged over the project's life (e.g., installments).
- **Total Received** = Σ all `PaymentRecord.amount` for the project.
- **Outstanding Balance** = `Total Contracted Revenue − Total Received − Σ active WriteOffRecord amounts` (§6.7.4). This is what's still owed and not yet resolved. Reversed write-offs (§6.7.5) are excluded from this sum, since they're no longer considered written off.
- **Realized Profit/Loss** = `Total Received − Total Project Cost` — this is the system's **primary, default profit/loss figure**, shown throughout the dashboard and project views, since it reflects actual cash outcomes rather than optimistic assumptions.
- **Contracted Profit/Loss** (secondary) = `Total Contracted Revenue − Total Project Cost` — shown alongside Realized P/L as a "best case if fully paid" reference, useful for healthy, currently-paying projects, and for the forecast (§6.9).

#### 6.7.2 Handling a Client That Has Not Fully Paid (Still Active)
- While a project is still `Active`/`Extended` and ongoing, Outstanding Balance simply reflects normal in-progress billing — the project detail view shows both Realized P/L (based on what's been paid so far) and Contracted P/L (what it should look like once fully paid), so admins can see if collection is falling behind cost accrual even before the project finishes.

#### 6.7.3 Project Cancellation (Mid-way Cancellation or Client Gone AWOL)
- A **"Cancel Project"** action is available on any `Active` or `Extended` project, requiring a **reason** (free text, required — this is the natural place to record "client went AWOL," "client cancelled contract," "scope cancelled by mutual agreement," etc.).
- Cancelling sets `status = cancelled`, `cancelled_at`, `cancelled_reason`. A cancelled project:
  - Is immediately removed from the pool of projects employees/core members can be newly allocated to (existing historical allocations are untouched).
  - No longer accrues Total Contracted Revenue expectations beyond what's already logged (i.e., no further extensions are expected, though a final adjustment extension can still be logged if needed to reflect a negotiated settlement).
  - Stops counting toward "Active Projects" on the dashboard and is excluded from the budget-vs-timeline forecast (§6.9), since there's no longer a future to forecast toward.
- Cancellation does **not** require the Outstanding Balance to be zero — that's handled separately via write-off (§6.7.4), since the two are distinct facts: "the project stopped" vs. "we don't expect to collect the rest."
- **Reopening a cancelled project:** `Cancelled` is **not** a permanent/terminal state — a **"Reopen Project"** action is available on any cancelled project (e.g., cancelled in error, or the client later returns/resumes the engagement), requiring a reason **and a new `end_date`** (the admin is prompted to set a fresh end date as part of the reopen action, since the original timeline has typically already lapsed by the time a project is cancelled). Reopening sets `status = active`, updates `end_date` to the newly provided date, clears the cancellation flags (with the prior cancellation preserved in `AuditLog`), sets `reopened_at`/`reopened_by`/`reopened_reason`, and restores the project to the normal active pool — it once again accepts stand-up allocations, resumes forecasting (§6.9) against the new timeline, and counts toward "Active Projects" on the dashboard.

#### 6.7.4 Write-Off (Bad Debt)
- On any project with a non-zero Outstanding Balance (cancelled or not — e.g., a still-open project with a client who's gone quiet can also have a stale balance written off if collection is deemed unlikely), an admin can record a **"Write Off"** action, creating a `WriteOffRecord`:
  - Specifies the **amount to write off** (up to the current Outstanding Balance) and a **required reason**.
  - Sets `amount`, `reason`, `created_by`, `created_at`, with `status = active`.
  - The written-off amount is subtracted out of future Outstanding Balance calculations and **excluded from Contracted Profit/Loss** going forward (so the secondary/"best case" figure doesn't keep showing money that will never come in).
  - **Does not affect Realized Profit/Loss** — since Realized P/L is already based only on cash actually received, a write-off doesn't change it; it simply formally closes the book on the unpaid portion.
  - Logged in Audit Logs (`BALANCE_WRITTEN_OFF`).
- Dashboard shows an org-wide **Total Written Off** figure (sum of `active` `WriteOffRecord` amounts) so leadership has visibility into accumulated bad debt across all clients/projects (see §6.13).

#### 6.7.5 Write-Off Reversal
- Write-offs are **reversible** — e.g., a client believed to be AWOL unexpectedly pays after all.
- A **"Reverse Write-Off"** action is available on any `active` `WriteOffRecord`, requiring a reason:
  - Sets that `WriteOffRecord.status = reversed`, with `reversed_at`, `reversed_by`, `reversal_reason`.
  - **Simultaneously requires creating a new `PaymentRecord`** for the amount actually collected (which may be less than, equal to, or — in unusual cases — different from the original written-off amount; the admin enters the real amount received). This `PaymentRecord` is linked back to the `WriteOffRecord` via `reversal_of_writeoff_id` so the two stay traceable to each other.
  - Reversing a write-off does **not** happen silently as a side effect of logging an unrelated payment — it's an explicit, deliberate action, since a write-off represents a formal accounting decision that shouldn't be undone implicitly.
  - Once reversed, the amount is excluded from **Total Written Off**, the Outstanding Balance recalculates without it, and the newly linked `PaymentRecord` flows into **Total Received** and **Realized Profit/Loss** exactly like any other payment (see §6.7.1).
  - Logged in Audit Logs (`WRITE_OFF_REVERSED`).

### 6.8 Profitability & Utilization Calculation

**Employee Daily Cost Rate** = `employee's effective monthly salary at that time / number of calendar days in that month` (weekends and holidays are **included** in the divisor — i.e., a flat calendar-day proration, not a working-day proration).

**Employee Cost (per project)** = Σ (for each stand-up entry where the employee worked on this project, or was on paid leave with no allocation that day — see §6.5.4) `Employee Daily Cost Rate × allocation %` (paid-leave days with no allocation are counted as organizational overhead cost, not attributed to any specific project).

**Core Member Cost (per project)** = Σ (for each calendar month the core member has an active `CoreMemberAssignment` on this project) the **day-weighted share** of their effective monthly salary for that month — calculated per day as `monthly salary ÷ days in month ÷ number of projects they were concurrently assigned to on that specific day`, summed across the days in the month. This means if a core member's concurrent project count changes mid-month (e.g., unassigned from one project partway through), the cost split adjusts day-by-day rather than using a single flat divisor for the whole month.

**Total Project Cost** = Employee Cost (per project) + Core Member Cost (per project)

**Project Profit/Loss** — see §6.7.1 for the **Realized** (primary) and **Contracted** (secondary) formulas, both of which subtract Total Project Cost.

**Employee Utilization** = for a given period, the employee's allocated time across all projects vs. their available working time (i.e., how "spread thin" or "underutilized" they are — an employee marked absent frequently, or with low total allocation, shows low utilization). **Core members are excluded from this metric** since it's derived from stand-up allocation, which doesn't apply to them.

**Client Profit/Loss** = Σ Realized Profit/Loss of all projects under that client (Contracted shown as secondary where relevant).

**Category Profit/Loss** = Σ Realized Profit/Loss of all projects under that category (Contracted shown as secondary where relevant).

### 6.9 Project Budget, Timeline & Forecasting
Every non-cancelled project has a **fixed budget** and a **fixed timeline** (`start_date` → `end_date`, §6.2). The system forecasts where the project is heading based on current cost run-rate from both employees and core members, and on payment collection pace:

- **Cost Run-Rate** = the project's cost (Employee Cost + Core Member Cost per §6.8) incurred over the **most recently completed calendar month**, used as the basis for projecting forward.
- **Elapsed Timeline %** = time elapsed since `start_date` ÷ total planned duration (`start_date` → `end_date`).
- **Projected Total Cost at Completion** = actual cost incurred to date + (Cost Run-Rate × remaining months until `end_date`, or until the current forecast date if the project has already passed `end_date` and is running under auto-extension).
- **Forecasted Profit/Loss (Contracted basis)** = Total Contracted Revenue to date − Projected Total Cost at Completion — this assumes the full contracted amount is eventually collected, since forecasting isn't meaningful against Realized revenue (which is inherently only "so far").
- The forecast is shown alongside the **actual-to-date Realized and Contracted** profit/loss on the project detail view, so admins can see "where we stand today (real cash)," "where we'd stand if fully paid," and "where costs are headed if nothing changes."
- If the Cost Run-Rate implies the project will exceed its budget before `end_date` is reached, the project is visually flagged (e.g., "Trending Over Budget") on the **dashboard and project view only** — this is a visual indicator, not an emailed notification, independent of the Project Health Indicator thresholds (§6.14).
- Cancelled projects are excluded from forecasting (§6.7.3), since there's no future left to project.
- The forecast recalculates automatically as new stand-ups are completed and core member assignments change.

### 6.10 VAT Tracking
- VAT rate defaults to **13%**, configurable in Settings (super admin only, since it affects all future project calculations).
- VAT is calculated **only on amounts actually received**, not on the full contracted budget — each time a `PaymentRecord` is logged, it generates a VAT liability of `payment.amount × vat_rate_applied` (using the project's snapshotted rate).
- Dashboard shows **Accumulated VAT (Unpaid)** as a running total across all such payment-derived VAT amounts, org-wide.
- An admin action **"Mark VAT as Paid"** clears the accumulated total (logs the cleared amount, date, and actor), starting a fresh accumulation period. A history of past VAT clearances should be viewable.
- Since VAT now tracks received payments rather than contracted budgets, an unpaid or written-off balance never generates a VAT liability in the first place — there's nothing to reverse if a client never pays.

### 6.11 AMC (Annual Maintenance Contract) Tracking
- When a project's status is set to **Closed**, a **"Set AMC"** action becomes available. (Cancelled projects do not get an AMC.)
- Setting AMC requires a **free-period end date** (the date until which maintenance is free).
- System states:
  - `Free Period` — within the free window.
  - `Reminder Due` — within the reminder lead time of the free-period end date. Default lead time is **7 days before expiry**, configurable in Settings (super admin only).
  - `Overdue` — free period has ended and no paid AMC has been arranged; system prominently reminds the admin to send the client an AMC offer/invoice.
  - `Cancelled` — client rejected the AMC.
- **Cancelling an AMC:** an admin/manager can take a **"Cancel AMC"** action (e.g., when the client rejects it), with an **optional remark** explaining why. This sets status to `Cancelled`, stops further reminders for that project, and is logged with `cancelled_at` and `cancelled_remark`.
- Reminders surface on the Dashboard and via **email** (email is the only reminder channel for now; in-app notifications may be considered in a future version).

### 6.12 Project Categories
- Seeded categories: `Design`, `Development`.
- Admin can add/edit/deactivate categories.
- Category-level profit/loss view (Realized, primary), matching the project/client-level breakdown.

### 6.13 Dashboard

**Date Range Selector**
- A date range filter (start date, end date) sits at the top of the dashboard.
- **Empty/unset range** → all stats show **overall (all-time) totals**, as today.
- **Valid range selected** → all dashboard stats recalculate to reflect **only activity within that range** — e.g., stand-up cost attribution, core member cost accrual, extensions, payments received, and VAT accrual that fall within the selected dates. Project/client/category profit-loss, top profitable/loss lists, VAT accumulation, and AMC reminders all respect the selected range where applicable (AMC reminders are inherently forward-looking regardless of a past date range, so they remain based on current date rather than the selected range).
- Clearing the range reverts to overall stats.

Displays:
- **Total Profit** (sum of positive **Realized** project P/L, within selected range or overall — this is the headline figure)
- **Total Loss** (sum of negative **Realized** project P/L, within selected range or overall)
- **Overall Profit/Loss %** (net Realized margin across all projects, within selected range or overall)
- **Total Outstanding** (sum of Outstanding Balance across all non-cancelled, non-written-off projects — visibility into money still owed)
- **Total Written Off** (sum of `write_off_amount` across all projects — visibility into accumulated bad debt, §6.7.4)
- **Active Projects** count / **Closed Projects** count / **Cancelled Projects** count
- **Top 5 Profitable Projects** and **Top 5 Loss-Making Projects** (ranked by Realized P/L, within selected range or overall)
- **Projects Trending Over Budget** (forecasted to exceed budget before completion — see §6.9)
- **Accumulated (unpaid) VAT** (on payments received, not on contracted totals — see §6.10)
- **AMC reminders** (projects with reminder due / overdue)
- **Category breakdown** (Realized profit/loss per category, within selected range or overall)
- **Project Health Indicators** (see §6.14) — visual flags (e.g., green/yellow/red) per project based on configurable thresholds, computed from Realized margin

### 6.14 Configurable Project Health Indicators (Settings)
- Admins (and super admins) can configure thresholds that classify a project's health, based on **Realized profit margin**. Sensible defaults (editable):
  - **Healthy** (green): profit margin **≥ 20%**
  - **At Risk** (yellow): profit margin **0% to 20%**
  - **Bleeding** (red): profit margin **< 0%** (i.e., a net loss)
- Thresholds apply org-wide and are reflected as visual badges throughout the dashboard, project list, and client view.
- These indicators are based on **Realized profit/loss to date**; the separate "Trending Over Budget" flag (§6.9) is based on the **contracted-basis forecast** and can differ from the current health badge.

### 6.15 Audit Logs
- Every create/update/delete action of consequence is logged: client, project, employee, core member (including salary changes and leave status), stand-up completion/edit, extensions, payments recorded, project cancellation, write-offs, VAT clearance, AMC changes, settings changes.
- **Visible only to Super Admin.**
- Filterable by:
  - **Action type** (e.g., "Salary Updated", "Project Closed", "VAT Cleared", "Payment Recorded", "Balance Written Off", "Write-Off Reversed", "Project Reopened")
  - **User (actor)**
  - Combinable filters (action **and/or** user)
- Each entry shows: timestamp, actor, action, target entity, and a readable diff/summary of what changed.
- **Retention:** logs are kept **indefinitely** for now (no automatic archival or deletion policy in v1).

## 7. Edge Cases & Business Rules

| Scenario | Handling |
|---|---|
| Employee salary increased mid-project | Historical cost calculations use the salary effective at the time of each stand-up; only future stand-ups use the new salary. |
| Core member salary increased mid-project | Same principle: months before the raise's `effective_from` use the prior salary; months after use the new salary. |
| Employee leaves the organization | Marked `left`, excluded from future stand-ups/active utilization views, but historical data is retained for reporting and audit. |
| Core member leaves the organization | Marked `left`; excluded from future cost accrual on all assigned projects going forward, but historical cost data is retained. |
| Employee marked absent, within paid leave allowance | Notes field disabled, no project allocation for the day, but the employee's prorated daily cost **is still counted** (as overhead) toward that day's cost calculation. Recorded as a paid leave day. |
| Employee marked absent, paid leave allowance already exhausted | Recorded as **unpaid leave**; employee is **excluded** from cost calculation for that day. Reflected in their month-wise unpaid leave history. |
| Allocation percentages don't sum to 100% | System blocks stand-up completion until corrected (validation error). |
| Employee selects a project they aren't assigned to, or that's cancelled/closed | Not selectable — the project list offered during a stand-up is restricted to the employee's assigned, still-active projects only. |
| Core member assigned to multiple concurrent projects | Their monthly salary is **divided across active assignments, prorated by day** — e.g., 3 concurrent projects for a full month each bear ⅓ of the salary as cost; the split recalculates day-by-day if the concurrent count changes mid-month. |
| Project extension with no amount entered | Amount defaults to `0`; still logged and added to Total Contracted Revenue (net effect zero, but not merely a note). |
| Project extension with amount but cost exceeds it | Flagged as a loss-generating extension once realized; reflected in Realized P/L and visually indicated (e.g., red badge). |
| Project reaches its end date without being closed | System **auto-extends** it (status → `Extended`, flagged `auto_extended`) with a fixed system reason and `amount = 0`; an **email is sent to all admins**; further manual extensions can be logged against it afterward. |
| Project's cost run-rate implies it will exceed budget before its end date | Flagged "Trending Over Budget" on the dashboard/project view only, independent of its current Realized health indicator color. |
| **Client has not fully paid the contracted budget (project still active)** | Outstanding Balance is visible on the project; Realized P/L reflects only what's been received so far, while Contracted P/L shows the full-payment scenario for comparison — no special action needed unless collection is at risk. |
| **Client goes unresponsive/AWOL** | Admin uses **Cancel Project** (§6.7.3) with a reason describing the situation, then **Write Off** (§6.7.4) the unrecoverable Outstanding Balance with a reason. Realized P/L is unaffected by the write-off (it already reflects only cash received); Contracted P/L and Outstanding Balance drop the written-off amount going forward. |
| **Project cancelled mid-way, client has paid only part of the budget** | Admin cancels the project (§6.7.3) with a reason. The amount already received via `PaymentRecord`s stays as-is and continues to drive Realized P/L. Any remaining Outstanding Balance can optionally be written off (§6.7.4) if it won't be collected, or left outstanding if collection is still expected/being pursued outside the system. |
| **A cancelled or AWOL client later resumes / pays again** | Admin uses **Reopen Project** (§6.7.3), providing a reason and a **new `end_date`** (prompted as part of the action, since the original timeline has usually lapsed). If a prior write-off exists for that amount, use **Reverse Write-Off** (§6.7.5) instead/in addition, which requires logging the actual new `PaymentRecord` alongside the reversal. |
| **A written-off balance is unexpectedly collected without reopening the project** | The write-off can be reversed (§6.7.5) independently of project status — reversal doesn't require the project itself to be reopened first (e.g., a cancelled project's stale balance can still be collected and reconciled after the fact). |
| VAT rate changed in Settings | Only applies to new payments going forward; already-recorded VAT on past payments retains the project's snapshot rate (`vat_rate_applied`) at the time each payment was logged. |
| Paid leave allowance changed in Settings | Applies going forward; historical paid/unpaid leave classification for past periods is not retroactively recalculated. |
| Two admins editing the same stand-up concurrently | Live cursors and real-time sync prevent silent overwrites; last-write-wins is avoided via collaborative editing (CRDT/OT). |
| Client deletion with active projects | Blocked; client must be deactivated instead, or all projects closed/cancelled first. |
| Dashboard date range left empty | Shows overall (all-time) stats. |
| Dashboard date range set to a valid range | All applicable stats (profit/loss, VAT accrued, top projects, category breakdown, payments) recalculate for that range only. |

## 8. Non-Functional Requirements

- **Real-time collaboration:** stand-up editing must support multiple concurrent editors with sub-second cursor/content sync.
- **Auditability:** audit logs must be immutable (append-only) and tamper-evident.
- **Data integrity:** salary history, VAT-rate snapshots, and payment records must never be altered retroactively by later configuration changes (a rate change or later edit shouldn't silently rewrite past figures).
- **Access control:** role-based permissions enforced at the API layer, not just UI.
- **Currency:** all monetary values stored and displayed in NPR.
- **Performance:** dashboard aggregate stats and forecasts should load quickly even as stand-up/allocation/payment history grows (consider pre-aggregation or caching for historical rollups).

## 10. Success Metrics

- % reduction in projects reaching "Overdue" AMC status without a reminder having been actioned.
- Time-to-detect a bleeding project (from project going negative to it being flagged on dashboard) — target: real-time/next stand-up cycle.
- % of projects where the forecasted profit/loss at the midpoint of the timeline matches the actual outcome at completion (forecast accuracy).
- Adoption: % of active employees appearing in completed stand-ups per week.
- Reduction in unpaid/untracked VAT discrepancies at audit time.
- Total Outstanding and Total Written Off trending down over time as a % of Total Contracted Revenue (collection health).
